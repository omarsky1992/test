## 1. فهم النظام (بعد إجابات المراجعة الأولى)

الجهة وكيل خدمة إنترنت. التفعيل الفعلي يتم يدوياً من **موقع الشركة الإلكتروني**، والنظام الجديد يسجّل كل ما يحصل مالياً وتشغيلياً ويحلّ محل الدفاتر.

### قاموس المصطلحات (مرجع ملزم لكل الوثائق)

| المصطلح | المعنى في النظام | الاسم التقني |
|---------|------------------|--------------|
| **المشترك** | الشخص (الزبون)، ويُعرَّف برقم هاتفه المسجل في الشركة. قد يملك أكثر من اشتراك (بيت أو أكثر) | `subscriber` |
| **الحساب** | اشتراك واحد على موقع الشركة: يوزر، باسورد، سيريال، هاتف، الفات، رقم العامود. غالباً ≤ 2 لكل مشترك | `account` |
| **الفئة / الكارت** | أساسي 35,000 · بلس 45,000 · تيربو 65,000 · برو ماكس 100,000 (سعر ثابت، مع عروض) | `service_plan` |
| **العرض** | تخفيض على سعر الفئة للمشتركين الجدد أو الحاليين | `promotion` |
| **تفعيل 7 أيام** | تفعيل بالدين لسعر الكارت كاملاً، يُكمَل لاحقاً بـ 23 يوماً | `activation (partial_7)` |
| **تفعيل 30 يوم** | تفعيل كامل مباشرة | `activation (full_30)` |
| **الإكمال** | إضافة 23 يوماً لتفعيل 7 أيام ليصبح 30 يوماً، ويحصل إما بالتسديد أو بالمناقلة | `completion` / `extension_23` |
| **الديون الثانوية** | ديون تفعيلات 7 أيام التي لم تُسدَّد ولم تُنقل بعد | `bucket = secondary` |
| **الديون الأولية** | الديون المنقولة من الثانوية، أو ديون 30 يوم الآجلة، أو الديون اليدوية | `bucket = primary` |
| **المناقلة** | عملية مستقلة تنقل دين حساب من الثانوية إلى الأولية وتضيف 23 يوماً | `debt_transfer` |
| **القبض** | دفع دين أو دفع مقدم، نقداً أو إلكترونياً مع اسم المستلم | `payment` |
| **السند** | سند القبض الناتج عن كل عملية قبض، يُعرض أو يُطبع عند الطلب | `receipt` |
| **المصروفات / المبيعات** | مصاريف الوكيل (شراء راوتر مثلاً) ومبيعات الأجهزة، والفرق بينهما يدخل الرصيد | `expense` / `device_sale` |
| **الصندوق / المحفظة** | مكان وجود المال: قاصة نقدية أو محفظة إلكترونية باسم مستلم | `money_account` |
| **الرصيد الابتدائي** | رصيد القاصة عند بدء النظام | `opening_balance` |
| **رصيد الشركة** | المبلغ المدفوع مسبقاً للشركة، ويُخصم منه سعر كل تفعيل | `COMPANY_BALANCE` |
| **الراجع** | ما تنزّله الشركة للوكيل بعد فترة (الربح من التفعيلات) | `company_settlement` |
| **الزون** | صندوق الشراء والتفعيل الذي يموّل الديون | `money_account` (القاصة التشغيلية) |
| **المتابعة** | قائمة الاتصال بمشتركي الـ7 أيام المتأخرين مع سجل الاتصالات | `follow_up` |

> ⚠️ **تصحيح مهم لفهم الـPRD:** «الأولي والثانوي» في الـPRD **ليسا نوعين من الحسابات**، بل **نوعان من الديون** (دلوان). أما تعدد الحسابات فيعني تعدد الاشتراكات (البيوت) للمشترك نفسه. التصميم مبني على هذا الفهم، فإذا كان خاطئاً يجب تصحيحه قبل أي شيء.

## 2. القرارات الأساسية

| # | القرار | السبب |
|---|--------|-------|
| D1 | **Modular Monolith** بـ Laravel + PostgreSQL + Filament (واجهة عربية RTL) | فريق صغير وعمليات إدارية كثيفة بالنماذج. أسرع وصول لنظام مستقر، ويمكن فصل الوحدات لاحقاً |
| D2 | المبالغ `BIGINT` بأصغر وحدة للعملة (IQD = 0 منازل عشرية) + `currency_code` | دقة كاملة بلا Floating-point، وجاهز لعملات أخرى |
| D3 | **دفتر أستاذ مزدوج القيد** (`financial_transactions` + `ledger_entries`) مخفي عن المستخدم | لا يُعدَّل أي رقم مالي أبداً. كل تصحيح قيد عكسي، وإجماليات الديون الثانوية والأولية والقاصة ورصيد الشركة تُستخرج من الدفتر مباشرة |
| D3b | سعر التفعيل **ليس إيراداً**: ذمة على المشترك مقابل الخصم من رصيد الشركة. الإيراد = الراجع + ربح المبيعات | يعكس العلاقة الحقيقية مع الشركة، فيظهر الربح الصحيح |
| D4 | «الحذف» المالي = **إلغاء (Void)** بقيد عكسي + سبب + سجل تدقيق | يلبّي طلب «حذف الدين للمدير» دون فقدان التاريخ |
| D5 | مدة التفعيل تُحسب في الخادم فقط: `ends_at = starts_at + N days` بتوقيت بغداد، مع قيد يمنع تداخل الفترات | يمنع أخطاء حساب تاريخ الانتهاء |
| D6 | التجديد يبدأ بعد انتهاء التفعيل الحالي (طابور) | إجابة السؤال 7 |
| D7 | طبقة تكامل مستقلة (Adapters + Staging + External IDs). الجداول الأساسية لا تعرف شيئاً عن موقع الشركة | موقع الشركة بلا API. نبدأ باستيراد Excel/CSV |
| D8 | البيانات المالية محلية فقط ولا تُمسّ بالمزامنة أبداً | منع التلاعب والتعارض |
| D9 | `branch_id` موجود من البداية | دعم الفروع (إجابة السؤال 20) |
| D10 | أرقام مستندات تسلسلية بلا فجوات لكل نوع وسنة (`R-2026-000001`) | قابلية التدقيق والرجوع للسند |

## 3. قرارات محسومة من المراجعة الثانية

| # | السؤال | القرار المعتمد |
|---|--------|----------------|
| Q1 | انتهت الـ7 أيام دون تسديد أو مناقلة | يبقى الدين ثانوياً، ويظهر في **قائمة المتابعة والاتصال** مع سجل للاتصالات (`follow_ups`) |
| Q2 | من متى تبدأ الـ23 يوماً؟ | من **وقت المناقلة أو التسديد**. إذا تم ذلك داخل الـ7 أيام، تبدأ بعد نهاية الـ7 أيام حتى لا تتداخل الفترات، فيكون المجموع 30 يوماً بالضبط |
| Q3 | التسديد الجزئي لدين 7 أيام | **لا يضيف أياماً** والدين في الثانوية. تُضاف الـ23 يوماً عندما ينتقل المتبقي إلى الأولية (المناقلة). شاشة القبض تعرض الخيارين معاً: «سدِّد جزئياً + انقل الباقي للأولية» |
| Q4 | 30 يوماً آجل | دين أولي مباشرة |
| Q5 | «الرصيد الابتدائي» | **رصيد القاصة** |
| Q6 | «رقم المشترك من الشركة» | هو **رقم هاتف الزبون المسجل في الشركة**: يصبح هو مفتاح التعرف على المشترك، واليوزر مفتاح الحساب |
| Q9 | تصدير Excel من موقع الشركة | **لا يوجد**. الاستيراد يكون بلصق جدول منسوخ من الصفحة، أو بالإدخال اليدوي، أو لاحقاً بأداة في المتصفح تقرأ الصفحة المفتوحة (انظر 07) |
| Q7, Q8, Q10 | إلغاء التفعيل الخاطئ، المحافظ، الفروع والاستضافة | **الافتراضات المكتوبة سابقاً معتمدة** ما لم تعترضوا: إلغاء التفعيل للمدير كتصحيح، قائمة محافظ، قاصة لكل فرع، وخادم سحابي |

### نموذج العلاقة المالية مع الشركة (من إجابة Q5)

- الوكيل يدفع للشركة **نفس سعر الاشتراك** عن كل تفعيل. إذن سعر الكارت **ليس ربحاً**، بل ذمة على المشترك يقابلها مبلغ دُفع للشركة.
- الربح الحقيقي هو **«الراجع»**: مبلغ تنزّله الشركة للوكيل بعد فترة (الراتب الكلي).
- الوكيل يقسّم الراجع، ويضيف جزءاً منه إلى **«الزون»**، وهو صندوق الشراء والتفعيل الذي يتحمّل تمويل ديون المشتركين.

التصميم أُعدّل على هذا الأساس. انظر `COMPANY_BALANCE` و`company_settlements` و`fund_transfers` في 02 و04.

## 4. أسئلة مفتوحة (افتراض مؤقت لكل منها)

| # | السؤال | الافتراض الحالي في التصميم |
|---|--------|---------------------------|
| Q11 | كيف تدفعون للشركة؟ (أ) **رصيد مسبق** تشحنونه على الموقع، وكل تفعيل يُخصم منه؟ أم (ب) الشركة **تحاسبكم لاحقاً** على مجموع التفعيلات؟ | (أ) رصيد مسبق: صندوق `رصيد الشركة`، يُشحن من القاصة، ويُخصم منه كل تفعيل |
| Q12 | «الراجع»: هل هو نسبة ثابتة لكل تفعيل (أي يمكن حسابه مسبقاً) أم مبلغ إجمالي تحدده الشركة؟ وهل يصلكم نقداً أم يُضاف إلى رصيدكم على الموقع؟ | مبلغ إجمالي يُسجَّل عند وصوله مع الفترة التي يغطيها، ويختار الموظف أين دخل (القاصة أو رصيد الشركة) |
| Q13 | «الزون»: هل هو اسم صندوق الشراء والتفعيل نفسه (القاصة)؟ والجزء الباقي من الراجع أين يذهب: سحوبات للشركاء، رواتب موظفين، أم غيرها؟ وهل تريدون تسجيله؟ | «الزون» = القاصة التشغيلية. الباقي يُسجَّل **توزيعاً** (سحب شركاء أو رواتب) بجهة ومبلغ |
| Q14 | العروض: من يتحمّل الخصم؟ الشركة (تخصم منكم السعر المخفض نفسه) أم أنتم؟ | حقل لكل عرض `funded_by`: الشركة أو الوكيل. إذا تحمّله الوكيل يُسجَّل مصروف خصم |
| Q15 | هل يعرض موقع الشركة **تاريخ انتهاء** الاشتراك لكل يوزر؟ | إذا نعم، يُستخدم لتقرير المطابقة (كشف التفعيلات غير المسجلة) |
